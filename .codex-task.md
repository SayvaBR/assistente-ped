# Codex Task — Android 1.0 Orchestrator

## Operating model

Do not work without a goal, and do not treat the entire Android 1.0 as the scope of one endless session.

Read first:

1. `docs/CODEX_GOAL_SYSTEM.md`
2. `docs/ANDROID_1_0_EXECUTION_BOARD.md`
3. `docs/CODEX_ANDROID_1_0_COMPLETION_MISSION.md`
4. `docs/INTEGRATION_BRANCH_POLICY.md`
5. `AGENTS.md`

Use the Android 1.0 mission as the **North Star**, not as a single-session task.

## North Star

> Um professor conseguiria confiar neste aplicativo amanhã durante uma aula real?

Final product state: `ANDROID 1.0 PRODUCT COMPLETION CANDIDATE`.

Never attempt to reach that entire final state inside one unbounded chat/PR.

## Start of every session

Run:

```bash
git status
git branch --show-current
git fetch origin --prune
git log -1 --oneline
```

Preserve local work. Never use destructive reset/clean/force push.

Historical branches/PRs are not active development fronts:

- `codex/1-import-baseline` / PR #2 — historical;
- `codex/design-identity-v2` / PR #4 — historical;
- PR #7 — historical;
- `codex/5-v2-clean-room` / PR #8 — frozen historical reference.

Current development parent: `integration/android-1.0`.

PR #10 is the consolidation train from integration to `main`; do not put normal feature work directly into it.

## Choose exactly one Delivery Unit

From `docs/ANDROID_1_0_EXECUTION_BOARD.md` and current open issues/PRs, select the highest-priority unblocked P0/P1 unit that can be delivered independently.

A Delivery Unit must be one bounded item, for example:

- one real V2 screen/flow;
- one integration between screens/data;
- one hardening pass;
- one P0 bug;
- one billing/restore slice;
- one storage migration;
- one QA/dev-ex slice.

Do not silently expand the unit into unrelated screens.

## Git rule for implementation

For normal feature/fix work:

1. start from updated `integration/android-1.0`;
2. create a small branch such as `codex/<issue>-<slug>`;
3. implement only the Delivery Unit;
4. push frequently;
5. open PR back to `integration/android-1.0`;
6. never target `main` directly for normal feature/fix work.

Do not implement normal features directly on `integration/android-1.0`.

## Visual work

Use the current visual/adaptive skills when relevant:

- `$assistente-pedagogico-rapid-ui`
- `$assistente-pedagogico-ui-screen-craft`
- `$assistente-pedagogico-android-adaptive-ui`

Fast loop:

`hypothesis -> implement -> render main viewport -> screenshot -> observe -> fix highest-impact issue -> screenshot again`

Do not spend the whole iteration manually benchmarking many viewport sizes. Use automated responsive checks at candidate/hardening checkpoints according to current Android cadence docs.

Visual identity:

Friendly Professional + Candy UI + Tactile + Educational + Motion-led.

No mascot/owl. No generic SaaS dashboard. No Material-default look. No card-for-everything pattern. No fake CTA or isolated demo screen disconnected from the real journey.

## Functional work

Prefer real user journeys over isolated screens.

Examples:

- Home -> Frequência -> alter status -> save -> reopen -> persisted;
- Home -> Observação -> select student -> save -> student history reflects it;
- Planning -> BNCC -> save -> restart -> plan persists -> Home/calendar reflects it;
- Onboarding -> setup -> subscription/restore -> Home.

Keep local-first/offline behavior where required.

## Quality invariants

Never trade these for speed:

- data integrity;
- LGPD/privacy;
- security;
- billing/entitlement correctness;
- backup/restore safety;
- BNCC/pedagogical correctness;
- offline essential flows;
- accessibility;
- no dead ends;
- no fake actions;
- no silent return to V1 in main journeys.

## Parallel agents

The main chat is the orchestrator.

Use parallel agents for independent work, but keep at most two concurrent write lanes unless there is a compelling reason and file ownership is disjoint.

Read-only reviewers/mappers may run in parallel.

Shared files such as router, global tokens, primitives, package/build config, storage/billing contracts and app shell have one owner per round.

## Candidate checkpoint

Before declaring the Delivery Unit ready:

1. run fast checks during iteration;
2. run candidate-level tests proportional to risk;
3. build when applicable;
4. run relevant responsive/accessibility checks;
5. run Android sync/APK QA when the unit crosses native/release risk boundaries;
6. attach real evidence/screenshots for UI changes;
7. update `docs/ANDROID_1_0_EXECUTION_BOARD.md`.

## Stop condition

When the current Delivery Unit is complete, stop expanding scope and report:

`READY FOR REVIEW — <DELIVERY UNIT>`

Include:

- branch;
- commit SHA;
- PR number targeting `integration/android-1.0`;
- evidence/screenshots when applicable;
- checks/tests run;
- known remaining issues;
- next recommended Delivery Unit.

`READY FOR REVIEW` means the unit is ready to be reviewed. It does not mean approved and does not authorize merge.

After that checkpoint, prefer a fresh session/agent for the next major Delivery Unit rather than letting one chat grow indefinitely.

## Core principle

**Be ambitious about the Android 1.0 outcome, but bounded about each execution.**

Advance one strong, reviewable Delivery Unit at a time until the North Star is achieved.
