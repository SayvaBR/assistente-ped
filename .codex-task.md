# Codex Task — Android 1.0 Continuous Orchestrator

## Operating model

Android 1.0 is a **continuous product mission**, but no single worker, branch or PR may become an unbounded mega-task.

The main Codex chat acts as an **orchestrator**. It may keep working for hours by creating fresh bounded Delivery Units in isolated branches/worktrees/agents, reviewing them, integrating safe ones into `integration/android-1.0`, and then moving to the next unblocked unit.

Do not keep one worker context implementing the whole app.

## Continuous orchestration loop

Repeat while safe, useful work remains:

1. sync repository state and inspect active PRs/issues/CI;
2. finish or review any Delivery Unit already near completion before starting duplicate work;
3. choose the highest-priority unblocked P0/P1 Delivery Unit;
4. create a fresh branch/worktree and preferably a fresh worker/subagent context;
5. execute only that Delivery Unit;
6. run evidence/tests proportional to risk;
7. open/update a small PR to `integration/android-1.0`;
8. run independent review agents;
9. fix concrete review findings in the same PR;
10. when the unit passes its gate, integrate it into `integration/android-1.0` only if the risk policy below permits it;
11. update `docs/ANDROID_1_0_EXECUTION_BOARD.md`;
12. discard/close the worker context, keep the orchestrator context, and start the next independent Delivery Unit with fresh context.

The orchestrator should not stop merely because one worker reported `READY FOR REVIEW`.

`READY FOR REVIEW` stops **that worker's scope expansion**, not the overall Android 1.0 mission.

## Delivery Unit rule

A Delivery Unit is one reviewable outcome, for example:

- one real screen/flow;
- one functional integration;
- one hardening pass;
- one P0/P1 bug;
- one billing/restore slice;
- one storage/backup slice;
- one Android QA/dev-ex slice.

Do not silently absorb unrelated screens into the same branch/PR.

## UI / visual gate

For any UI change, functionality alone is not approval.

Required behavior:

1. run the real surface;
2. render in the current main Android work viewport (412 CSS px unless the target requires direct comparison at another width);
3. capture a **fresh screenshot after every significant visual change**, aiming for roughly a 5–10 minute visual feedback loop when practical;
4. inspect composition, hierarchy, spacing, typography, identity and interaction states;
5. use `visual_director` or equivalent independent reviewer;
6. record the 3–5 highest-impact perceptual differences/problems;
7. correct the highest-impact issue;
8. capture a **new screenshot after the correction**;
9. only then move toward the candidate gate.

Do not declare UI `READY FOR REVIEW` without sufficient fresh visual evidence.

Reject UI that is merely functional but generic, inconsistent, inaccessible or visibly lower quality than the V2 standard.

Identity:

Friendly Professional + Candy UI + Tactile + Educational + Motion-led.

Never use mascot/owl. Avoid generic SaaS dashboard, fintech, Material-default, glassmorphism, generic gradients, card-for-everything layouts and fake CTAs.

Do not run Android/full E2E on every CSS micro-adjustment. Deep validation belongs at candidate/PR/release checkpoints according to risk.

## Functional gate

Prefer real journeys over isolated screens:

- Home -> Frequência -> alter status -> save -> reopen -> persisted;
- Home -> Observação -> select student -> save -> student history reflects it;
- Planning -> BNCC -> save -> restart -> persisted -> Home/calendar reflects it;
- Onboarding -> setup -> subscription/restore -> Home.

No fake primary action, dead end, data loss, or silent fallback to V1 in a main journey.

## Review agents

Before integration, use independent review where relevant:

- visual/UI: `visual_director` + `qa_reviewer`;
- code/data: independent code/QA reviewer;
- high-risk domain: targeted specialist/reviewer.

A worker does not self-approve its own Delivery Unit.

## Integration risk policy

### LOW RISK — may integrate into `integration/android-1.0` automatically after gates

Examples:

- isolated visual polish with screenshots and accessibility preserved;
- copy/spacing/layout corrections;
- non-destructive UI bugfixes;
- tests, screenshots, DevEx tooling;
- small logic bug with strong regression test and no data schema impact.

Requires:

- PR is mergeable;
- CI green on exact head;
- relevant tests green;
- independent reviewer has no blocking finding;
- UI evidence complete when applicable.

### MEDIUM RISK — integrate only after stronger agent review

Examples:

- normal feature logic;
- local persistence behavior without schema migration;
- navigation involving multiple real flows;
- offline/recovery behavior.

Requires LOW RISK gates plus at least one targeted independent reviewer and journey-level test/evidence.

### HIGH RISK — do not auto-integrate; require human checkpoint

Includes:

- billing, purchases, entitlement, trial/restore;
- storage schema migrations;
- backup/restore that can overwrite or destroy data;
- authentication/account deletion;
- privacy/LGPD/security-sensitive changes;
- permissions/secrets/keystore/release signing;
- destructive operations;
- changes that materially alter BNCC/pedagogical data semantics;
- merge/release to `main` / Play Store.

If a high-risk unit is waiting for human review, record the blocker and continue another independent safe Delivery Unit. Stop the orchestrator only when no safe independent work remains.

## Candidate checkpoint for each Delivery Unit

Before reporting a unit ready:

1. fast checks during iteration;
2. candidate-level tests proportional to risk;
3. build when applicable;
4. responsive/accessibility checkpoint where relevant;
5. Android sync/APK QA when native/release risk requires it;
6. real screenshots/evidence for UI;
7. execution board update;
8. PR opened to `integration/android-1.0`.

Report:

`READY FOR REVIEW — <DELIVERY UNIT>`

Include branch, SHA, PR, evidence, tests, known issues and next recommended unit.

The orchestrator then reviews/integrates according to risk and continues.

## Overall stop conditions

The continuous mission stops only when one of these is true:

1. `ANDROID 1.0 PRODUCT COMPLETION CANDIDATE` is objectively reached;
2. no safe independent Delivery Unit remains because all remaining work is blocked by human/external/high-risk decisions;
3. a serious security/data-integrity incident requires immediate human intervention;
4. repository/CI state is unsafe or inconsistent and must be reconciled before more work;
5. execution environment/rate limit prevents further work.

Do **not** stop merely because one Delivery Unit is ready for review.

## Core principle

**Ambition is continuous; implementation contexts are disposable.**

Keep the orchestrator running, but keep every worker, branch and PR small, fresh, reviewable and replaceable.
